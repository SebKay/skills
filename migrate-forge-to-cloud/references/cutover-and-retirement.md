# Cutover and Retirement

## DNS Preparation

- Read Cloud's exact record names, types, targets and proxy mode for the custom hostname. Keep the old routing values for rollback. Use pre-verification where supported and coordinate ownership or certificate records in advance. Some already-proxied Cloudflare setups require real-time verification. Budget for it in the maintenance window. [Laravel Cloud domains](https://laravel.com/cloud/docs/domains.md)
- If the user owns DNS, give them the exact record changes and when each should be applied. Replace conflicting records for the same hostname. If Cloud asks for a DNS-only certificate delegation that replaces Forge's existing `_acme-challenge` record, save the old value and check the current Forge certificate's validity before replacing it. Apply the authorized delegation ahead of the traffic change when supported, and verify that the public hostname still reaches Forge. Include the old delegation in the pre-write rollback if Forge needs it for renewals. Keep Cloud's required delegation in place after cutover.
- Avoid assuming a proxy from Forge to a Cloud test URL will preserve the public hostname. Verify routing, TLS, login and signed URLs before relying on a proxy during propagation.

## Production Cutover

1. Confirm the agreed window, the DNS operator's availability, usable access to both environments and a rollback decision point. Before freezing Forge, verify the intended Cloud deployment has succeeded and that runtime commands, the write fence and the target data connections work on that release. A pending deployment can block runtime commands even while the previous release serves traffic.
2. Fence every writer to the scoped data on Forge, including web traffic, scheduled jobs and direct database or storage clients. Let in-flight requests and jobs finish before taking the final baseline. Stop or pause the scoped consumers and account for waiting, delayed and reserved jobs per queue. Check the actual runtime state if a Forge stop request remains pending. For Horizon, confirm that the scoped process is stopped or that its workers are paused and in-flight jobs have finished. Preserve other sites on the server. Inspect schedules that can run in maintenance mode and check that write-capable routes such as webhooks and token endpoints actually receive the maintenance response.
3. Transfer the final database, sync durable files and object storage changes, and move any remaining job or session state for this site. Keep destination writers fenced during restore and baseline comparison. If Cloud must remain in maintenance across a deployment or across replicas, rehearse cache-backed Laravel maintenance mode with an environment-scoped store. Ensure the deploy commands and restore preserve the maintenance key. Confirm the fence with real HTTP requests after the deployment and the restore. Run pending migrations in the rehearsed order and verify the resulting schema, state and runtime connections before letting workers or the scheduler perform production work. [Cloud maintenance mode](https://laravel.com/cloud/docs/compute.md#maintenance-mode)
4. Once the final copy and destination checks pass, tell the DNS operator that the site is ready for the DNS switch. Hand over the confirmed routing records or apply them if authorized. Keep existing callback URLs when the public hostname is preserved. Where supported, verify public routing and TLS before enabling Cloud writes and side-effecting jobs. When both origins serve maintenance responses, use a harmless marker unique to Cloud or confirm the request in Cloud logs. If the handoff requires Cloud to accept writes sooner, treat that as the point after which a simple rollback is unsafe. Keep Forge fenced and run one set of consumers and scheduled jobs.
5. Verify live service using the checks below. Confirm every Cloud deployment left the intended settings in effect. Restore any temporary cutover build or deploy commands before enabling Push to Deploy and verify the regular deployment path.

If cutover fails before Cloud accepts production writes or emits external effects, keep Cloud fenced and use the tested rollback path within the agreed window, including coordinating any DNS reversal. Once Cloud has new production writes or external effects, prefer fixing Cloud in place. If rollback is necessary, fence both sides and checkpoint Cloud's data. Verify the Forge release can run with the reconciled schema. Bring across new database writes, files and pending jobs, and account for external effects before restoring Forge as the sole writer and reversing DNS. Keep the user informed if the handoff exceeds the window.

## Verify Live Service

- Confirm the DNS provider's configured record and Cloud's hostname, certificate and origin verification. With a proxied record, public DNS can return the proxy addresses. Check fresh HTTPS requests to the canonical hostname and confirm they reach Cloud using access logs or equivalent origin evidence. If needed, `curl --connect-to` can probe Cloud's instructed target with the canonical hostname and TLS verification intact. Check the old Forge origin directly where possible and confirm it still rejects app writes. If the proxy reports an error such as Cloudflare 1014 or 1016 during provisioning, check the target and Cloud verification status within the agreed rollback window before changing proxy mode.
- Verify the login page and assets, then test an authenticated flow with an approved account if available. Check existing media URLs and a disposable upload, read and cleanup through each relevant public or private disk. Check canonical OAuth redirects and exercise the full sign-in flow when access permits. For webhooks, use a provider test delivery or a signed event whose handler you have confirmed has no production side effects. Report which checks reached the live app and which flows were proven only in rehearsal.
- Verify the expected workers and queue assignments after redeploy. Where safe, dispatch a disposable job to each relevant queue and check a completion marker or equivalent outcome. Test queued mail to an authorized recipient when relevant and distinguish provider acceptance from mailbox delivery. Confirm the monitoring agent and look for fresh production telemetry where accessible.
- Verify a naturally scheduled run from Cloud after the next due time, using logs or an observable result such as a new metrics snapshot for an app that schedules `horizon:snapshot`. A manual `schedule:run`, `schedule:list`, or an enabled toggle alone cannot prove the scheduler ran on Cloud. Choose a low-risk event and avoid invoking customer-facing scheduled work just to test it.
- Verify the capture time of the newest completed backup against the final restore so you know whether it covers the imported production data. If a post-cutover backup or isolated restore test is outside scope, report the recovery coverage actually verified. [Laravel MySQL backups](https://laravel.com/cloud/docs/resources/databases/laravel-mysql.md#database-backups)

## HTTP Runtime Parity

- Compare Forge's effective proxy and PHP-FPM limits with Cloud's request timeout, body and upload limits, and available memory. Use requests through the public ingress to verify representative slow requests, multipart uploads and streamed downloads when the app uses them. Account for time spent in decoders, external calls and object storage. Use the existing workload to choose limits. Check the installed CLI for supported options such as `cloud environment:update --timeout`.
- Check live response headers on routes with intentional exceptions, including authenticated iframes and private pages. Test embedded pages in a signed-in browser. If Cloud adds a blanket framing restriction, give the specific response a Content Security Policy `frame-ancestors` directive for its intended parent origins where appropriate. Keep the app's broader anti-framing protections. [Content Security Policy](https://www.w3.org/TR/CSP3/#directive-frame-ancestors)
- If links carry access tokens in URL paths or query strings, send unique synthetic values through the public host and inspect Cloud access logs for them. Check this even when Forge access logs were disabled or application telemetry redacts tokens. If Cloud still receives token-bearing URLs, address them before the layer that records them, for example through a narrowly scoped upstream rewrite. If the rewrite depends on app code, deploy that code before enabling it and reverse the order on rollback. Recheck existing links, form submissions, cache and referrer headers, and use an unrelated request to confirm log delivery. Keep real tokens out of probes and reports.

## Production Cloud Settings

Apply these defaults for the migrated production environment unless the user specified different settings.

- Set the environment's display name to **Production** and its color to green. Use `cloud environment:update` with `--name=Production --color=green` where supported.
- Enable the **Scheduler** on the app server at cutover, after Forge's scheduler is fenced. Use `cloud instance:update --uses-scheduler=true` and verify a scheduled run after deployment. [Cloud scheduled tasks](https://laravel.com/cloud/docs/scheduled-tasks.md)
- Use **Scale to Zero** with a 300-second idle timeout for the app server, database cluster and cache where the workload permits. For the app and Valkey, the CLI takes minutes. Use `--scale-to-zero=true --scale-to-zero-timeout=5` for the app and `--uses-hibernation=true --hibernation-timeout=5` for Valkey. For supported database clusters, use `--suspend-seconds=300` where the current CLI exposes it, or set the matching timeout in the dashboard. Verify support on the selected tiers and account for other environments using a shared resource. [Cloud compute](https://laravel.com/cloud/docs/compute.md#scale-to-zero) · [Laravel MySQL](https://laravel.com/cloud/docs/resources/databases/laravel-mysql.md#scale-to-zero) · [Laravel Valkey](https://laravel.com/cloud/docs/resources/caches/valkey.md#scale-to-zero)
- Verify queue behavior during sleep, or record why the app stays awake. Laravel schedules can wake the app, and frequent schedules can keep it awake. Time-sensitive jobs need independent processing when the app sleeps. Use managed queues or an always-awake worker cluster when available and compatible. For a small app that needs Horizon and whose plan disallows dedicated clusters, a custom `php artisan horizon` process on an always-awake App cluster preserves the queue setup without changing plans. Size compute for both web and worker load. Confirm the expected Horizon master count because each replica starts the configured processes, and check for unintended consumers on the same queues. Report any deviation from the Scale to Zero defaults. [Cloud workers](https://laravel.com/cloud/docs/workers.md) · [Scheduled tasks and queues](https://laravel.com/cloud/docs/compute.md#scheduled-tasks-and-queues)
- After public HTTPS and the affected subdomains are verified, enable **Strict-Transport-Security** in Edge Network settings with `includeSubDomains` and `preload`. Use Cloud's one-year max-age (`--hsts-max-age=31536000 --hsts-include-subdomains=true --hsts-preload=true`) unless the user specifies another value. Verify the header on the public HTTPS hostname. Treat browser preload-list submission as a separate action that requires a request. [Cloud network settings](https://laravel.com/cloud/docs/network.md) · [HSTS preload requirements](https://hstspreload.org/#submission-requirements)
- Keep **Push to Deploy** disabled during preparation and cutover. Complete any redeploy required by the runtime settings and verify the public site. Then enable it on the intended deployment branch with `cloud environment:update --uses-push-to-deploy=true` and confirm the saved setting.
- If cutover uses a temporary branch, return to the normal release branch after its migration changes land through the repository's review process. Check Forge's deployment triggers before an authorized merge. Verify the expected commit is on the normal branch before switching Cloud to it. Check whether the branch switch starts a deployment and trigger one if needed. Verify the deployed commit, Push to Deploy and live behavior. [Laravel Cloud deployments](https://laravel.com/cloud/docs/deployments.md)

## Source Retirement

Verify current conditions before saying that the Forge server can be powered off:

- Confirm the public DNS target and TLS verification, recent requests on Cloud, and working Cloud database, cache, workers and scheduler. Check old aliases, application connection settings, webhook or callback hosts, and any still-routed nonproduction names. Check whether rendered media, stored URLs or uploads still depend on a Forge-managed bucket before retiring that bucket.
- Inventory every Forge site, database, worker, scheduler or cron entry, monitor and backup configuration on the server. Inspect listening services, active clients and available recent logs for remaining dependencies. A point-in-time connection check cannot rule out infrequent consumers. Say when access logs are unavailable.
- Identify data that exists only on Forge, such as a staging database or local files outside the original migration scope. Verify Cloud backup or recovery settings and record what needs an archive before permanent deletion. Keep the Forge database available during the agreed recovery period.
- Distinguish a reversible power-off from server deletion or billing cancellation. Perform retirement actions only when authorized for the exact server.
