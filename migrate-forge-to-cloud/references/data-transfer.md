# Data Transfer

Choose the source and target using confirmed resource IDs and effective runtime connections. Keep the initial rehearsal and final copy distinguishable. Rehearse with the same restore path, provider versions, extensions and data shape that the cutover will use. Inspect foreign keys, sequence or auto-increment state, special column types and jobs before accepting a restore on counts alone.

## PostgreSQL

- Use a compatible `pg_dump` client and a custom-format dump. Check the source and destination versions, extensions such as pgvector, extension schemas and target role privileges. Use a supported direct connection for the restore when the runtime uses a pooler.
- For a database local to Forge, a fast path is to run `pg_dump` on Forge and run `pg_restore` from Forge to the verified Cloud endpoint over TLS. This keeps the source database private and avoids relaying the expanded restore through a laptop. Use an SSH tunnel or another authenticated private transfer path when direct access is unavailable.
- Use a private archive and a protected client credential source. Keep credentials out of command arguments, shell history and deployment logs. Exclude source ownership and ACLs when Cloud manages roles. Check for app-specific grants that must be recreated intentionally. For an appropriate-size archive, `pg_restore --no-owner --no-privileges --single-transaction --exit-on-error` rolls back a failed restore.
- Restore into an empty or explicitly disposable destination. Use `--clean --if-exists` only when the exact destination is verified as an isolated rehearsal copy that can be replaced. Keep unrelated environments, schemas and roles out of the operation. For larger datasets where a single full restore would exceed the agreed window, rehearse a staged copy and measured catch-up before committing to that window.

## MySQL

- Confirm engine versions, storage engines, character sets and collations, SQL modes, and managed-server privileges. Use a consistent logical export and include app-owned views, triggers, routines and events where used. `--single-transaction` provides a snapshot for transactional tables. Nontransactional tables need a separate consistency plan.
- Rehearse import into a dedicated database. Review definer accounts, GTID statements and event scheduler behavior before import. MySQL DDL can commit implicitly, so recover a partial import by rebuilding the disposable destination or restoring a known checkpoint. Check [Laravel's Forge migration guide](https://laravel.com/cloud/migrate-forge-cloud) for the current service-specific import options.

## Redis and Valkey

- Identify which connections hold queues, sessions, locks and disposable cache. Preserve the operational state the app needs. Drain running jobs first, and account for waiting, delayed and reserved jobs. Keep just one set of consumers active. Use the [Valkey migration guide](https://laravel.com/cloud/docs/knowledge-base/migrate-upstash-to-valkey.md) for transfer and validation options.
- Verify the DB indices and key prefixes on both ends. Cloud may map source keys from multiple DB indices into one destination DB. Detect collisions before importing. If environments share Valkey, verify isolation for keys, queue consumers and cache operations. Preserve key types and expiry times, check binary restore compatibility, and skip stale lock keys or Horizon's live process registrations unless their migration is intentional.
- Use a supported private import path or run the import from the destination environment. Keep Valkey private. Prove the transfer with isolated keys or a disposable environment before copying live sessions or jobs. Confirm the actual queue depth and session behavior after cutover.
- For live sessions, preserve the absolute expiration through the transfer and skip keys that expire before import. If the source and destination support compatible binary dumps, Redis `RESTORE ... ABSTTL` accepts the absolute expiration in milliseconds. Verify on the destination without printing session IDs or payloads. If isolated environments need a temporary relay, use an authenticated private location, encrypt the payload before uploading, and remove and verify removal of the relay object and local copies after import. [Redis RESTORE](https://redis.io/docs/latest/commands/restore/)

## Files and Verification

- Inspect shared storage paths and symlink targets on Forge. Move durable local uploads to persistent storage. Cloud deployment filesystems are ephemeral.
- At the write freeze, capture source counts and integrity checks for the scoped data. Where the rehearsed window allows, compare table-content digests using consistent row serialization and deterministic ordering. For PostgreSQL, compare sequence values and their called state, plus foreign-key definitions and validation state. After restore, compare against the frozen baseline before allowing destination writes and account for intentional changes from migrations. Check app-visible data, encrypted fields and a representative query for required database extensions. Report what was sampled or excluded. Remove temporary endpoints or database access you enabled for transfer once the app uses its intended connection.

## Object Storage

- Inventory the effective default and named disks, bucket identifiers, object prefixes and public base URLs. Include durable originals, conversions, responsive images and attachments, plus temporary uploads needed by work in progress. Use an object inventory alongside database counts. On a shared bucket, scope the transfer to the app and environment. Record which buckets will move and which independently managed stores will stay.
- For disks moving to Laravel Cloud Object Storage, attach the destination to the intended environment and preserve disk names and object keys where practical. Use separate buckets for public and private content when both are needed. Verify the S3 endpoint and actual bucket identifier from the connection details. The dashboard display name can differ from the S3 bucket name. Check destination file type restrictions, browser upload CORS, signed URLs and lifecycle rules as applicable. Confirm the installed Laravel and storage adapter support the planned configuration. [Laravel Cloud Object Storage](https://laravel.com/cloud/docs/resources/object-storage.md)
- Copy durable objects and relevant metadata such as content type and cache control. For mutable files, copy in bulk before the cutover, then fence the app, conversion workers and direct upload writers before syncing the final changes. Preserve temporary uploads still needed and record any expired uploads excluded. Compare the destination key set, sizes and checksums to the scoped source inventory. Multipart ETags can differ for identical content, so use content checksums when ETags are insufficient. A supported [read-through disk](https://laravel.com/cloud/docs/knowledge-base/migrating-object-storage.md) can cover server-side reads during a staged move. Check how direct public URLs resolve and account for objects the app rarely reads before removing a fallback.
- Review persisted media URLs and custom CDN domains. Preserve working URLs or update references that depend on the old bucket. Review custom disk configuration and storage environment overrides that can take precedence over Cloud-managed settings. After redeploying, verify effective disk endpoints and generated URLs, then test a read and a disposable upload through the app, including a browser-signed upload when used. Check fresh public pages and their actual media responses after cutover. Purge caches that still serve old URLs. Retain source objects through the rollback period.
